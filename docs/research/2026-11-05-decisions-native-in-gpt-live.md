# How OpenAI pairs the Decisions API with GPT-Live, and what of it we can use (2026-11-05)

This note records what OpenAI's own documentation says about running the Decisions API inside a GPT-Live session, read on the afternoon of 2026-11-05 while pilot 4 ran, after the Decisions path of 2026-11-04 (branch `decisions`) had failed three device runs. The question was whether a more direct use of the API exists than the one we built, which called `POST /v1/decisions` from our own process on every frame and on every transcript.

## Sources

- The Decisions guide, `developers.openai.com/api/docs/guides/decisions`, and the create reference, `/api/reference/resources/decisions/methods/create`.
- The voice guide, `/api/docs/guides/decisions-voice` ("Connect voice to Decisions"), the only page that describes the native integration.
- The Live API reference, `/api/reference/resources/live`: the session configuration, the client events `decision.create`, `decision.item.create`, `decision.item.delete`, the server events `decision.event`, `decision.item.created`.
- The Python SDK `openai` 3.46.0 (`openai/types/live/decision_*.py`, `decisions_delegation_config_param.py`, `decision_trigger_param.py`) and `livekit-agents` 1.8.10 with `livekit-plugins-openai` 1.8.10, downloaded as wheels and read.

## The Decisions API itself

One model, `gpt-6-luna`. Three question types: `predicate` (a probability), `choice` (2 to 255 options, a distribution and a confidence), `score` (2 to 10 ordered levels, the expected index). One to 400 questions a request, answered independently on one shared `input`. The input is a string or a list of items: user messages with `input_text`, `input_image` (a data URL or a public URL, `detail` low, high, auto or original) and `input_json`; developer and system messages with text only; assistant messages; function and custom tool calls with their outputs. Question `instructions` may themselves carry text, images and JSON. Prompt caching puts an implicit breakpoint at the end of the input, needs a prefix of at least 1,024 tokens, and allows explicit breakpoints with a 30 minute lifetime. Input costs $0.10 per million tokens, output is free, and the guide claims answers "about 10x faster than the Responses API". There is no `service_tier` and no `reasoning` field.

## The native integration in GPT-Live

GPT-Live can run Decisions by itself in two ways, both evaluated on the conversation's transcript and on a set of shared Decision items the application appends.

**Delegation to Decisions.** The session is started with `delegation: {type: "decisions", decisions: {model: "gpt-6-luna", questions: [...]}}`, at most 64 questions, and an `acknowledgement_delay_ms` of 0 to 800 (400 by default). The session's instructions say when GPT-Live hands a request off; each question's instructions say what Decisions picks. When GPT-Live hands off, the application receives `session.delegation.created` and then a `decision.event` carrying `event.type: "decision.completed"` and the answers by question name; it runs the action the answers select, appends the new state as a Decision item, and reports back with `session.commentary.append` under the delegation's id. The guide's example is a car: three choice questions (cabin temperature up, down or none; defogger on, off or none; whether the rest of the request needs the Responses API), the application turning the knobs and, for the rest, calling Responses itself. The delegation type is fixed for the session's life.

**Triggers on the transcript.** `session.triggers` holds at most two triggers, one per direction: `event_type: "session.input_transcript.delta"` for the user's words, `"session.output_transcript.delta"` for GPT-Live's own, each with up to 64 questions. Every transcript delta is evaluated against the questions, and the result comes as a `decision.event` with the trigger's id and the delta's `source_event_id`, while the user is still speaking. Deltas may be merged and results may arrive out of order, so the newest applicable result wins. Triggers run independently of the delegation type and can be set, replaced or disabled at any time with `session.update` (waiting for `session.updated`). The guide's example animates a digital person: "I got the job!" makes it smile and nod before the sentence is over.

**Shared Decision items.** `decision.item.create` appends an item "for future decisions without starting an evaluation or changing Live voice context": a user message, which may carry `input_image` and `input_json`, a developer, system or assistant message, or a function call and its output. `decision.item.delete` removes one. `decision.create` (with a unique `event_id`) evaluates the configured questions now, on the conversation and the items. The guide's advice is to append a compact snapshot of the application's state when it changes and to leave earlier items in place, so the cached prefix holds; "the latest snapshot counts as current".

**What the native path does not do.** Decisions on the Live side never hears audio; it reads transcripts. Images reach it only as items the application appends or inside question instructions. Nothing in the guide concerns a camera, and the model behind it is the same `gpt-6-luna` whose reading of our frames is measured in `eval/brain-decisions/` on the `decisions` branch: hand on the plate and brick on the plate crisp, the brick's identity and the exactness of a placement not.

## What the SDKs support

`openai` 3.46.0 has every type above. `livekit-agents` 1.8.10 adds a `DecisionModel` abstraction over `POST /v1/decisions` (`livekit/agents/llm/decisions.py`, `livekit/plugins/openai/decision_model.py`), the standalone API our eyes called by hand. Its GPT-Live model, moved into `livekit/agents/llm/_realtime/gpt_live.py`, still knows only the `client` and `responses` delegation types and nothing of triggers or `decision.*` events. Two things make the native path reachable all the same, in 1.8.3 as in 1.8.10: `send_event` accepts a raw dict, so `session.update` with triggers, `decision.item.create` with a frame and `decision.create` can be sent without SDK types, and every raw server event is emitted as `openai_server_event_received`, which `gpt/agent.py` already listens to, so `decision.event` can be read. A `decisions` delegation type would need the session start configuration patched (`_build_delegation`), since the plugin writes it.

## What it would mean for this system

The native integration is about when, not about seeing. It moves the classification of the wearer's words into GPT-Live's own session, where it runs on each transcript delta against the shared items, and it lets the application keep a frame and the build's state in those items so that every decision, triggered or delegated, sees them. What it would replace of the `decisions` branch: our own transcript classifier and the piece-joining and settling around it, a hop of 0.3 to 1 s, and the hand-over closing by guesswork. What it would not change: the model's limits on the frame, so the judgement of a placement would still go to the brain's model, and the eyes' two reliable questions, a brick held and the step's brick on the plate with no hand on it, would still be the events that call it.

A sketch, not built: GPT-Live with a trigger on the wearer's transcript asking what they want (a check of the placement, of the brick in hand, the picture, the place again, nothing) and a trigger on its own transcript asking whether it has just said it will look; the agent appending the newest frame as a Decision item every few seconds with the one before deleted, and the build's state as JSON when it changes; a `decision.event` answering within the wearer's sentence, on which the agent takes the frame to the brain's model or shows the picture, and closes the turn with `session.commentary.append`. The first thing to measure, before any of it: whether the LiveKit plugin passes a trigger set through `session.update` and a frame through `decision.item.create`, and how long a `decision.event` takes after a transcript delta, on one session with `eval/voice-script`.
